---
title: Review angle reference
description: The review lenses, automatic detection rules, and model tier for each angle.
---

A review angle is a concern to check, such as correctness, security, database behavior, or
accessibility. A bounded low-risk local review uses one worker to cover the relevant concerns.
Broader, riskier, CI, audit, or explicitly configured reviews use specialists. An independent
adjudicator checks proposed findings against evidence, and receipts record the work each reviewer did.

## Angle selection

The [detector](https://github.com/howarewoo/woostack/blob/main/skills/woostack-review/scripts/detect-angles.sh)
defines automatic selection. It starts with correctness and adds angles based on changed paths,
changed lines, or verified context. Before starting workers, it may combine a bounded low-risk local
review into one `general` pass. That pass covers correctness, security and compatibility, simplicity,
project rules, acceptance criteria, documentation, and tests.

Explicit force/skip settings preserve specialist selection. `force` wins a tie; the base `bugs`
pass cannot be skipped. See [angle selection](/docs/configuration#angle-selection).

## Angle catalog

The catalog describes each concern. The detector contains the automatic path and text rules;
each angle's prompt metadata sets its default worker tier. Angles can also be explicitly selected.

| Angle | Concern |
| --- | --- |
| `general` | Holistic bounded local review, including applicable rules and approved intent |
| `acceptance` | Approved acceptance criteria and contract claims |
| `aeo` | AI-crawler access and structured answer-engine content |
| `api` | Routes, public contracts, schemas, and wire compatibility |
| `architecture` | Boundaries, coupling, and structural quality |
| `bugs` | Evidence-backed correctness and broken behavior |
| `comments` | Comment accuracy; findings are non-blocking |
| `conventions` | The repository's own applicable rules |
| `database` | Integrity, migrations, transactions, queries, and access control |
| `deps` | Dependency compatibility and hygiene |
| `design` | Visual design, UX, and accessibility |
| `docs` | Accuracy of documentation affected by the change |
| `i18n` | Translation catalogs and message usage |
| `infra` | CI, containers, deployment, and infrastructure definitions |
| `observability` | Logging, diagnostics, and silent failures |
| `production-readiness` | Operational failure handling and resource limits |
| `security` | Injection, authorization, secrets, and unsafe data flows |
| `seo` | Search metadata, crawling, and indexing |
| `simplify` | Unnecessary code, duplication, and needless abstractions |
| `skills` | The validated changed Agent Skill package |
| `tests` | Observable behavior coverage and test quality |


<Callout type="info">
  `comments` findings are always non-blocking. Automatic selection adds `conventions` when prefetch
  finds applicable repository rules, and `acceptance` when it resolves the intent governing the
  change. Explicit configuration can request these angles too, but they still need their supporting
  context. Only the adjudicator can use a verified later-increment `woostack-defer(<ref>)` marker to
  turn matching missing work into a visible non-blocking finding. Security findings cannot be deferred.
</Callout>

## Pre-flight use

[`woostack-harden`](/docs/skills/woostack-harden) uses relevant review concerns as questions while
checking a specification or plan against repository evidence. It always checks the premise: does
the evidence support the stated problem or constraint? Other questions apply only where relevant.
Harden raises one discrepancy at a time and waits for the user's decision.

[`woostack-plan`](/docs/skills/woostack-plan) checks the ordered increments and their contracts.
Neither owns an approval gate. These planning checks do not replace pull request review of the code.

## Tiers

A tier selects the level of model work: `fast` for rubric and pattern checks, `standard` for
reasoning-heavy passes, and `deep` for the independent evidence adjudicator. Prompt metadata supplies
defaults; supported overrides can change the effective tier or model.
[Context management](/docs/concepts/context-management#isolated-agents-receive-bounded-envelopes)
links to the host-specific routing rules, including OMP's host-owned roles. See
[model selection](/docs/configuration#model-selection) for overrides.
